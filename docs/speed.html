Speed

Everything runs on one laptop. NEAT needs far more simulated flights than PPO did, so speed decides how many generations fit before the deadline. Every speed-up here is measured end to end (flights per second, generations per hour), before and after.

The machine (measured 2026-11-01)

CPUIntel Core i5-8250U, 4 cores / 8 threads, up to 3.4 GHz
RAM7.6 GB (+ 4 GB swap)
GPUIntel UHD 620 only: no usable GPU, so everything is CPU
SoftwarePython 3.12, gymnasium 0.29.1 (Box2D 2.3.5), numpy 1.26, g++ 13.3, pybind11

Rules: workers × threads ≤ 8, one BLAS thread per worker process (8 workers × 8 threads once gave a load of 34), narration and video rendering with nice.

The budget

The last project: the Python reference simulator ran ~18,000–20,000 steps/s across 8 processes. A NEAT generation of 300 genomes × 32 flights × ~300 steps is about 3 M steps: ~2.5 minutes, so only ~500 generations a day. The target is ≥ 10× faster: Box2D itself took only 1.5 µs of the 117 µs per step measured before; the rest was Python glue. The plan: compile the same Box2D 2.3 in C++, port the lander's step logic and evaluate the network in C++, so one call flies a whole batch with no Python in the loop.

The rule that keeps it honest: the C++ simulator is for training only, after a test shows the same seeds and actions give the same outcome on ≥ 98% of 1,000 flights and the same agent's landing rate falls inside the reference's confidence interval. All checks, the selection and the goal test run in the Python reference.

Wall time for the first two phases is estimated with that same ~6 s. Wall clock: ~101 → ~19 s per generation, about 5.3×, ~190 generations an hour.

Short of the 10× target. The profile says why: the old figure of 1.5 µs for Box2D was wrong for this env. gymnasium asks Box2D for 180 velocity and 60 position iterations per step, and box2d-py's own world.Step measured about a third of the whole Python step. C++ removes the Python around it, not the solver, and fewer iterations would change the physics.

8 workers beat 7 in all three alternating pairs, by ~2%. From 4 to 8 workers it is only ~17% faster: the laptop has 4 physical cores and the second thread of each core adds little. N1 runs with 8 workers from gen 327. The top 10's 40 re-flights per generation now fly lander/fastenv.py, the reference env's numbers step for step; the checks and the champion's selection flights still fly the reference env itself.

What changed. (1) NeatJsonNet picks its action with a numba kernel: 5 µs instead of 46 µs per call on a 551-connection network, the same action. (2) lander/fastenv.py: the frozen flight minus gymnasium's wrapper layers, numpy scalar maths and per-step RNG calls; step-by-step identical inputs, actions and results (test in tests/test_core.py). (3) sim/lander_sim.cpp: the same Box2D 2.3.x source box2d-py 2.3.5 wraps, the world rebuilt in gymnasium's order, every random number drawn in Python with gymnasium's own RNG, the network in C++. lander/env.py is untouched (its sha256 test still passes).

The equivalence test (experiments/cpp_equivalence.py, results/cpp_equivalence.json): the gen-266 champion on 1,000 analysis seeds in three worlds (the real task, the stage-2 wind world, calm air). The C++ flights are bit-identical to a fresh reference env on 3,000 of 3,000. Against a reused reference env the outcome matches on 99.9%, 99.7% and 100%, exactly as often as the reference matches itself: a reused env differs in the last bits after touchdown because Box2D reuses the ids of destroyed bodies. Landing rates are inside the reference's confidence interval in all three worlds. Checks, the selection re-flights and the goal test still fly the reference env.
